## §3. 실행 프롬프트 본문 (Copy-and-Paste 영역)

> 아래 블록 **전체** 를 새 Cursor 세션에 그대로 붙여 넣으십시오.
> 한 번의 실행으로 TDD 설계 문서가 산출됩니다.

```markdown
# [실행용 프롬프트] Magic Square 4x4 — TDD 설계 문서 작성

당신은 **TDD(Test-Driven Development) 설계 전문가**입니다.
이전 세션에서 STEP 1~5(관찰 → 3-Why → 진짜 문제 정의)가 이미 완료되어,
다음의 자산이 확정된 상태입니다. 이를 **이번 작업의 전제(Given)** 로 받아들이십시오.

────────────────────────────────────────
[확정된 전제 — 변경 불가]
────────────────────────────────────────

■ 진짜 문제 정의
"4×4 격자 위에서, 1~16의 자연수를 중복 없이 배치하였을 때
모든 행(4)·열(4)·대각선(2)의 합이 Magic Constant = 34를 만족하는 상태가
존재하는가를 판단하고, 그 상태를 **생성·검증·표현**의 책임을 분리하여
다룰 수 있는가."

■ 핵심 Invariant 계층
- Level 0 (구성)  : 4×4=16칸, 1~16 각 정확히 한 번
- Level 1 (합산)  : 4 row · 4 col · 2 diag 각각의 합 = 34, 서로 독립
- Level 2 (파생)  : Magic Constant = n(n²+1)/2, n=4 일 때 34 (하드코딩 금지)
- Level 3 (설계)  : generate / validate / display는 서로 독립
                    검증은 생성 방식을 알지 못한다
                    표현은 생성·검증 어느 쪽에도 의존하지 않는다

■ 훈련 목표
조건의 완전한 열거 · 불변 조건의 선언 · 책임 분리 ·
표면/본질 구분 · 성공 기준의 사전 정의.

────────────────────────────────────────
[당신이 수행할 작업]
────────────────────────────────────────

위 전제를 바탕으로 **TDD 설계 문서**(Markdown 단일 문서)를 작성하십시오.

────────────────────────────────────────
[엄격한 제약 조건]
────────────────────────────────────────
1. 구현 코드(production code)를 작성하지 마십시오.
2. 테스트 코드 본문(실제 실행 가능한 코드)도 작성하지 마십시오.
   — 테스트의 "명세(specification)"만 작성합니다.
3. 특정 프로그래밍 언어 문법에 종속되지 마십시오.
   타입·시그니처는 의사 표기(pseudo-signature)로만 표현합니다.
   예: `generate() -> Board`, `validate(board: Board) -> Result`
4. 알고리즘(백트래킹, Siamese 등) 선택은 이 문서의 범위가 아닙니다.
   — 어떤 알고리즘으로 구현하든 동일하게 통과해야 할 **검증 계약**만 정의합니다.
5. Magic Constant 34는 **상수가 아니라 유도값**으로 다뤄야 합니다.
6. 모든 결정은 위 Level 0~3 Invariant 중 어느 것에서 유래했는지 **추적 가능**해야 합니다.

────────────────────────────────────────
[출력 형식 — 다음 7개 SECTION을 이 순서대로 작성]
────────────────────────────────────────

## SECTION 1 — Test List (검증 대상의 완전한 목록)
- "무엇이 참이어야 하는가"의 목록만 작성. 코드 금지.
- 각 항목에 다음을 반드시 표기:
  · ID (T01, T02, ...)
  · 검증하려는 명제 (한 문장)
  · 출처 Invariant (Level 0/1/2/3 중)
  · 검증의 종류 (Example-based / Property-based / Boundary / Negative)
- Level 0~3 모든 Invariant가 **적어도 하나의 T**로 커버되는지 표로 검증
  (Traceability Matrix: Invariant ↔ Test ID).

## SECTION 2 — Domain Model & Module Boundary
- 도메인 어휘(Cell, Row, Column, Diagonal, Board, MagicConstant 등)를 정의.
  · 각 개념의 정의 1~2줄
  · 어떤 Invariant를 표현하기 위해 존재하는가
- 세 모듈의 경계를 명시:
  · Generator (생성 책임)
  · Validator (검증 책임)
  · Presenter / Display (표현 책임)
- "Validator는 Generator의 내부를 알지 못한다"는 Level 3 조건이
  모듈 경계에서 어떻게 강제되는지 1문단으로 설명.

## SECTION 3 — Function Contracts (입출력 계약)
- 각 공개 함수에 대해 다음을 표 또는 블록으로 정의:
  · 의사 시그니처 (pseudo-signature)
  · 입력 (Input) — 형식·허용 범위
  · 출력 (Output) — 형식·보장 사항
  · 사전조건 (Precondition)
  · 사후조건 (Postcondition) — Level 0/1/2 Invariant와의 매핑
  · 실패 모드 (Failure Mode) — 어떤 상황에서 어떻게 실패를 표현하는가
- 최소 다음 함수의 계약을 포함:
  · `generate() -> Board`
  · `validate(board) -> ValidationResult`
  · `magic_constant(n) -> int`   ← n으로부터 유도, 34 하드코딩 금지
  · `display(board) -> str`

## SECTION 4 — Test Specification (Given / When / Then)
- SECTION 1의 모든 T(ID)에 대해 1:1로 Given-When-Then 명세를 작성.
- 형식 예시(문장만, 코드 아님):
    [T03] 모든 행의 합은 Magic Constant 와 같다
      Given : 유효한 Board 한 개
      When  : 각 행의 합을 계산했을 때
      Then  : 4개 합 모두 magic_constant(4) 와 같다
- Property-based 후보에는 "어떤 무작위 입력에서도 늘 참인 속성"임을 명시.

## SECTION 5 — Red → Green → Refactor 진행 순서
- 작성 순서를 의존성에 따라 번호로 매기십시오 (1, 2, 3 ...).
- 각 단계마다:
  · 어떤 T(ID)를 먼저 Red로 만드는가
  · Green을 위해 도입되는 최소 구조는 무엇인가 (코드 아님, 묘사)
  · Refactor 단계에서 통합되어야 할 중복/추상은 무엇인가
- 원칙: Level 0 → Level 1 → Level 2 → Level 3 순서로 올라가도록 정렬.
  하위 Level 이 깨진 상태에서 상위 Level Test 를 작성하지 않는다는 근거 1줄 포함.

## SECTION 6 — Edge Cases & Negative Tests
- 다음 카테고리별로 최소 2개씩 케이스를 명세:
  · 구성 위반   (예: 17이 등장, 1이 누락, 같은 수 중복)
  · 형태 위반   (예: 3×4 격자, 5×5 격자, 빈 격자)
  · 합산 위반   (예: 행만 만족, 대각선만 누락)
  · 타입 위반   (예: 정수가 아닌 값, null/None)
- 각 케이스가 어떤 실패 모드(Failure Mode)와 매핑되는지 SECTION 3과 연결.

## SECTION 7 — 통합 검증 전략 & Done의 정의
- 단위 테스트 / 속성 기반 테스트 / 통합 테스트의 역할 분담을 표로 정리.
- 회귀(Regression) 보호 전략:
  알고리즘을 교체해도 동일 Test List 가 100% 통과해야 함을 명시.
- "이 시스템이 완성되었다"고 선언할 수 있는 **사전 정의된 Done 기준**을
  체크리스트로 작성 (Level 0~3 Invariant 모두 커버 + Traceability 100%).

────────────────────────────────────────
[작성 톤과 스타일]
────────────────────────────────────────
- 한국어로 작성합니다.
- 단정적이고 검증 가능한 문장만 사용합니다. ("~인 것 같다" 금지)
- 모든 결정에 **근거(어느 Invariant에서 왔는가)** 를 1줄로 부기합니다.
- 표(Table)와 목록을 적극 활용하되, 추상적 수사는 배제합니다.

────────────────────────────────────────
[작성 금지 사항 — 위반 시 무효]
────────────────────────────────────────
- 실행 가능한 코드 블록 (production / test 양쪽 모두)
- 특정 언어 표준 라이브러리 호출
- 알고리즘 비교 또는 성능 분석
- "Magic Constant = 34" 를 상수로 하드코딩한 표현
- Invariant 계층(Level 0~3)에 매핑되지 않는 임의의 Test 또는 결정

────────────────────────────────────────
[최종 산출물]
────────────────────────────────────────
SECTION 1~7 을 모두 포함하는 단일 Markdown 문서.
문서 끝에 다음 두 가지를 부록으로 첨부:
- 부록 A : Invariant ↔ Test ID Traceability Matrix
- 부록 B : "이 설계가 STEP 1~5 의 진짜 문제 정의를 어떻게 만족시키는가" 1문단 자기 검토

지금부터 위 사양에 따라 TDD 설계 문서를 작성하십시오.
```

## §4. 산출물 검증 체크리스트

본 프롬프트를 실행하여 얻은 TDD 설계 문서는 다음을 모두 만족해야 한다.
하나라도 어긋나면, 동일 세션 내에서 보완 요청한다.

- [ ] SECTION 1 ~ SECTION 7 이 누락 없이 존재한다
- [ ] 부록 A 의 Traceability Matrix 가 작성되었고, Level 0~3 전 항목이 1개 이상의 T 로 커버된다
- [ ] 실행 가능한 코드 블록이 한 줄도 포함되지 않는다
- [ ] "34" 가 상수가 아니라 `n(n²+1)/2` 형태로 유도된다
- [ ] SECTION 5 의 진행 순서가 Level 0 → 1 → 2 → 3 으로 정렬되어 있다
- [ ] `generate` / `validate` / `display` / `magic_constant` 네 함수의 Contract 가 SECTION 3 에 모두 존재한다
- [ ] 부록 B 의 자기 검토가 STEP 1~5 의 진짜 문제 정의와 명시적으로 연결되어 있다
- [ ] 한국어로 작성되었고, "~인 것 같다" 류의 비결정적 표현이 없다

## 메타 노트

본 트랜스크립트는 **"설계 문서를 만들기 전에, 설계 문서가 만족해야 할 조건을 먼저 선언한다"** 는
STEP 1~5 의 핵심 원칙을 한 단계 위로 끌어올린 것이다.

> Invariant 를 선언하고 Test 를 먼저 쓰는 것이 코드를 통제하듯,
> 이 프롬프트는 **설계 문서를 통제** 한다.

§3 의 실행 프롬프트 본문은 다른 AI 모델·다른 세션에서 동일한 결과를 재현하기 위해 작성되었으며,
산출물의 품질은 §4 체크리스트로 객관적으로 측정 가능하다.
