## 1. 설계 배경

STEP 5까지의 문제 정의가 도달한 결론은 다음과 같다.

> "마방진 문제를 TDD로 설계하는 이유는,
> 제약 조건을 모두 이해했는가라는 질문에 대한 답을
> 실행 가능하고 반복 검증 가능한 형태로 증명하기 위해서이다."

이 결론은 **TDD 설계 문서의 필요성**을 도출했으나, 동시에 다음 위험을 함께 노출시켰다.

| 위험 | 설명 |
|---|---|
| 미끄러짐(Slipping) | "TDD 설계"를 요청하는 순간, AI 또는 사람이 곧장 코드 작성으로 미끄러진다 |
| 임의성 | 어떤 테스트를 작성할지, 어떤 모듈을 둘지가 작성자의 주관으로 결정된다 |
| 추적 불가 | 작성된 테스트가 어느 Invariant에서 유래했는지 사후에 검증 불가능해진다 |
| 재현 불가 | 다른 세션·다른 AI에서 같은 결과가 재현되지 않는다 |

따라서 STEP 6에 진입하기 전에, **결과물의 형식·범위·금지 사항을 사전에 구조화한 실행용 프롬프트**가 필요하다는 결론이 도출되었다.

## 2. 프롬프트 설계 원칙

본 프롬프트는 다음 원칙 위에 설계되었다.

### 원칙 ① — 전제(Given)의 명시적 고정
STEP 1~5의 결과(Invariant Level 0~3, 진짜 문제 정의, 책임 분리 원칙)를 프롬프트 본문에 **변경 불가 블록**으로 삽입한다.
→ 컨텍스트 누락·드리프트(drift)를 구조적으로 차단.

### 원칙 ② — 산출물 형식의 강제(Schema 주도)
"좋은 설계 문서를 작성하라"가 아니라, **SECTION 1~7 + 부록 A·B**라는 정해진 스키마를 채우도록 요구한다.
→ 작성자의 주관과 우연을 제거하고, 누락 항목을 즉시 감지 가능하게 함.

### 원칙 ③ — 금지 사항의 명시(Negative Constraint)
"코드 금지", "Magic Constant 하드코딩 금지", "알고리즘 선택 금지" 등을 명시한다.
→ "이런 것을 하지 말라"는 제약은 "이런 것을 하라"는 지시보다 항상 더 강한 통제력을 가진다.

### 원칙 ④ — 추적 가능성(Traceability)의 강제
모든 Test와 모든 결정에 출처 Invariant(Level 0~3)를 부기하도록 강제한다.
부록 A에 Invariant ↔ Test ID 매트릭스를 의무화한다.
→ "왜 이 테스트가 여기 있는가?"라는 질문에 항상 답할 수 있는 문서가 된다.

### 원칙 ⑤ — Done의 사전 정의
STEP 2에서 발견한 "성공 기준의 부재" 문제를 반복하지 않기 위해,
프롬프트 자체가 "Done의 정의"를 SECTION 7에서 사전에 작성하도록 요구한다.

## 3. 프롬프트 구조

```
┌──────────────────────────────────────────┐
│ [역할 부여]                              │
│   당신은 TDD 설계 전문가입니다.          │
├──────────────────────────────────────────┤
│ [확정된 전제 — 변경 불가]                │
│   · 진짜 문제 정의 (STEP 5 결과)         │
│   · 핵심 Invariant Level 0~3             │
│   · 훈련 목표 5가지                      │
├──────────────────────────────────────────┤
│ [수행할 작업]                            │
│   TDD 설계 문서 (Markdown) 작성          │
├──────────────────────────────────────────┤
│ [엄격한 제약 조건] 6개                   │
│   1. 구현 코드 금지                      │
│   2. 테스트 코드 본문 금지               │
│   3. 언어 종속 금지                      │
│   4. 알고리즘 선택 금지                  │
│   5. Magic Constant 유도 강제            │
│   6. Invariant 추적 가능성 강제          │
├──────────────────────────────────────────┤
│ [출력 형식 — SECTION 1~7]                │
│   1. Test List                           │
│   2. Domain Model & Module Boundary      │
│   3. Function Contracts                  │
│   4. Test Specification (G/W/T)          │
│   5. Red-Green-Refactor 진행 순서        │
│   6. Edge Cases & Negative Tests         │
│   7. 통합 검증 전략 & Done의 정의        │
├──────────────────────────────────────────┤
│ [작성 톤·금지 사항]                      │
├──────────────────────────────────────────┤
│ [최종 산출물]                            │
│   SECTION 1~7 + 부록 A (Traceability)    │
│                + 부록 B (자기 검토)      │
└──────────────────────────────────────────┘
```

## 4. 각 SECTION의 설계 의도

| SECTION | 강제하는 사고 능력 | 출처 Invariant |
|---|---|---|
| 1. Test List | 조건의 완전한 열거 | Level 0~2 |
| 2. Domain Model & Module Boundary | 책임 분리 | Level 3 |
| 3. Function Contracts | 입출력 명확성, 이해의 증명 | Level 0~3 |
| 4. Test Specification | 불변 조건의 선언, Given/When/Then 명시 | Level 0~2 |
| 5. Red → Green → Refactor 순서 | 의존성 사고, 하위 Level 우선 | Level 0 → 3 |
| 6. Edge Cases & Negative Tests | 표면/본질 구분, 실패 경로 명세 | Level 0~1 위반 케이스 |
| 7. 통합 전략 & Done | 성공 기준의 사전 정의 | Level 3 + 훈련 목표 ⑤ |
| 부록 A | 추적 가능성 | 전체 |
| 부록 B | 자기 검토 | 전체 |

이로써 STEP 5에서 정의한 **5가지 훈련 사고 능력**이 SECTION 구조에 1:1로 매핑된다.

## 5. 본 프롬프트가 미끄러짐(Slipping)을 차단하는 방식

| 미끄러짐 시나리오 | 차단 장치 |
|---|---|
| "일단 코드부터 짜볼게요" | 제약 조건 1, 2 (구현·테스트 코드 금지) |
| "Python으로 작성하면..." | 제약 조건 3 (언어 종속 금지) + 의사 시그니처 강제 |
| "백트래킹으로 풀면 더 빠르니까..." | 제약 조건 4 (알고리즘 선택 금지) |
| "magic_constant = 34" | 제약 조건 5 (n으로부터 유도) |
| "행 합 테스트만 있으면 충분" | SECTION 1 + 부록 A (Invariant 전체 커버 의무) |
| "통과하면 끝" | SECTION 7 (Done 기준 사전 정의 의무) |
| "다른 세션에서 다른 결과" | [확정된 전제] 블록 (입력 고정) + Schema 강제 |

## 6. 검증 — 본 프롬프트는 STEP 1~5의 결론을 만족하는가

| STEP 결론 | 본 프롬프트의 대응 |
|---|---|
| STEP 1: 제약 조건이 강한 배치 문제이다 | SECTION 1이 모든 제약을 테스트 항목으로 강제 열거 |
| STEP 2: "완성"이 성공 기준을 은폐한다 | SECTION 7이 Done 기준을 사전 정의 항목으로 강제 |
| STEP 3: 프로그램은 이해를 증명한다 | SECTION 3 Contract가 입출력 명확성을 강제 |
| STEP 4: TDD는 불변을 먼저 선언한다 | SECTION 1 Test List가 SECTION 5 진행 순서보다 먼저 작성 |
| STEP 5: 생성·검증·표현은 분리된다 | SECTION 2 Module Boundary + SECTION 3 함수별 Contract |

5개 결론 모두에 대해 1:1 대응 장치가 존재한다.

## 7. 사용 절차

1. 새 Cursor 세션을 연다.
2. `Prompt/tdd-design-prompt-transcript.md` 의 실행 프롬프트 블록 전체를 복사한다.
3. 그 한 블록을 새 세션에 그대로 붙여 넣고 실행한다.
4. 산출된 TDD 설계 문서를 `Report/tdd-design-document.md` 로 저장한다. (이후 단계)
5. 산출물이 부록 A의 Traceability Matrix를 충족하는지 검증한다.
   - 모든 Invariant(Level 0~3)가 1개 이상의 T(ID)로 커버되어야 한다.
   - 충족하지 못한 항목이 있으면, 프롬프트로 동일 세션에서 보완을 요청한다.

## 8. 산출물 평가 기준 (체크리스트)

본 프롬프트로 생성된 TDD 설계 문서는 다음을 모두 만족해야 한다.

- [ ] SECTION 1~7이 누락 없이 존재한다
- [ ] 부록 A의 Traceability Matrix가 작성되었고, Level 0~3 전 항목이 커버된다
- [ ] 실행 가능한 코드 블록이 한 줄도 포함되지 않는다
- [ ] "34"가 상수가 아닌 `n(n²+1)/2`로 유도되는 형태로 등장한다
- [ ] SECTION 5의 진행 순서가 Level 0 → 1 → 2 → 3 으로 정렬되어 있다
- [ ] generate / validate / display 세 함수의 Contract가 SECTION 3에 모두 존재한다
- [ ] 부록 B의 자기 검토가 STEP 1~5의 진짜 문제 정의와 명시적으로 연결되어 있다
